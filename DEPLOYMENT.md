# Deployment

The live demo runs on free tiers:

| Part | Host | Defined in |
|---|---|---|
| PostgreSQL database | Render | [`render.yaml`](render.yaml) |
| FastAPI backend | Render | [`render.yaml`](render.yaml) |
| React frontend | Vercel | _see "Frontend on Vercel" below_ |

## Before you start

1. **Push your code to GitHub.** Render and Vercel deploy from the repository, not from your computer.
2. **Choose your frontend address now.** Vercel gives each project `https://<project-name>.vercel.app`. Pick a name, for example `north-street-booking`. The backend needs this address to allow requests from it (CORS). If the name turns out to be taken, you can change the value later.
3. **Choose a strong admin password** of at least 12 characters, and store it in a password manager. The API refuses to start with a weak one.

## Backend and database on Render

1. Sign up at https://render.com with your GitHub account.
2. Click **New → Blueprint**, select the `booking-system` repository, and click **Connect**.
3. Render reads `render.yaml` and shows the database `north-street-db` and the web service `north-street-api`. It asks for the values marked `sync: false`:

   | Variable | What to enter |
   |---|---|
   | `ADMIN_PASSWORD` | Your strong admin password |
   | `CORS_ORIGINS` | Your frontend address, e.g. `https://north-street-booking.vercel.app`. **No trailing slash** |

   `JWT_SECRET` is generated by Render, and `DATABASE_URL` is filled in from the database automatically. Neither one ever appears in git.
4. Click **Apply**. Render creates the database, installs the requirements, runs `alembic upgrade head` (which creates all tables and the double-booking constraint) and starts the API.
5. When the service shows **Live**, open `https://north-street-api.onrender.com/api/v1/health`. Use the URL shown at the top of the service page if yours is different. You should see `{"status":"ok", ...}`.
6. Open `https://north-street-api.onrender.com/docs` to see the API documentation.

### If the deploy fails

Open the service, then the **Logs** tab:

- **`Unsafe production configuration: …`**: the message lists which variable is wrong. Fix it under **Environment** and save; Render redeploys automatically.
- **An error during `alembic upgrade head`**: copy the log and look at the last lines. The previous working version keeps running until a new deploy succeeds.

### Add the demo data

A fresh database has no barbers or services. Add them through the app itself:

1. Log in at `<your frontend>/admin` with `admin` and your admin password.
2. Go to **Team & services** and add a few barbers and services.

Don't run `scripts/seed_dev_data.py` against production: it deletes all bookings.

## Free-tier limitations

These are fine for a portfolio demo, but good to know (and to mention when you show it):

- **Cold starts:** the free API sleeps after 15 minutes without traffic. The first request after that takes about a minute; the admin login shows "Logging in…" while it waits.
- **No confirmation emails:** free Render services can't connect to SMTP ports (25/465/587), so `SMTP_HOST` is empty and emails are skipped. Bookings work normally. To enable email, use an HTTP-based email API (for example Brevo or Resend, both of which have free tiers), or a paid Render instance with the `SMTP_*` variables set.
- **Database lifetime:** free Render Postgres databases **expire 30 days after creation**, with a 14-day grace period before deletion. To keep the demo running longer, upgrade the database, or create a new free one and redeploy. Migrations recreate the schema; the demo data has to be added again.
- **Migrations run at startup:** pre-deploy commands are a paid feature, so `alembic upgrade head` runs in the start command. If a migration fails, the new version doesn't start and the previous one keeps serving.

## Updating the live app

Push to `main`. Render redeploys the API automatically (`autoDeploy: true`), including any new migrations.
