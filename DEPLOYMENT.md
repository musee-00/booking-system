# Deployment

The live demo runs on free tiers:

| Part | Host | Defined in |
|---|---|---|
| PostgreSQL database | Render | [`render.yaml`](render.yaml) |
| FastAPI backend | Render | [`render.yaml`](render.yaml) |
| React frontend | Vercel | [`frontend/vercel.json`](frontend/vercel.json) + project settings below |

## Before you start

1. **Push your code to GitHub.** Render and Vercel deploy from the repository, not from your computer.
2. **Choose your frontend address now.** Vercel gives each project `https://<project-name>.vercel.app`. Pick a name, for example `north-street-booking`. The backend needs this address to allow requests from it (CORS). If the name turns out to be taken, you can change the value later.
3. **Choose a strong admin password** of at least 12 characters, and store it in a password manager. The API refuses to start with a weak one.

## Backend and database on Render

1. Sign up at https://render.com with your GitHub account.
2. Click **New → Blueprint**, select the `booking-system` repository, and click **Connect**.
3. Render reads `render.yaml` and shows the database `north-street-db` and the web service `north-street-api`. It asks for the values marked `sync: false`:

   | Variable | What to enter |
   |---|---|
   | `ADMIN_PASSWORD` | Your strong admin password |
   | `CORS_ORIGINS` | Your frontend address, e.g. `https://north-street-booking.vercel.app`. **No trailing slash** |

   `JWT_SECRET` is generated by Render, and `DATABASE_URL` is filled in from the database automatically. Neither one ever appears in git.
4. Click **Apply**. Render creates the database, installs the requirements, runs `alembic upgrade head` (which creates all tables and the double-booking constraint) and starts the API.
5. When the service shows **Live**, open `https://north-street-api.onrender.com/api/v1/health`. Use the URL shown at the top of the service page if yours is different. You should see `{"status":"ok", ...}`.
6. Open `https://north-street-api.onrender.com/docs` to see the API documentation.

### If the deploy fails

Open the service, then the **Logs** tab:

- **`Unsafe production configuration: …`**: the message lists which variable is wrong. Fix it under **Environment** and save; Render redeploys automatically.
- **An error during `alembic upgrade head`**: copy the log and look at the last lines. The previous working version keeps running until a new deploy succeeds.

### Add the demo data

A fresh database has no barbers or services. Add them through the app itself:

1. Log in at `<your frontend>/admin` with `admin` and your admin password.
2. Go to **Team & services** and add a few barbers and services.

Don't run `scripts/seed_dev_data.py` against production: it deletes all bookings.

## Frontend on Vercel

Deploy the backend first, so you know its address.

1. Sign up at https://vercel.com with your GitHub account.
2. Click **Add New… → Project** and import the `booking-system` repository.
3. Configure the project:

   | Setting | Value |
   |---|---|
   | Project Name | The name you chose earlier, e.g. `north-street-booking` |
   | Framework Preset | **Vite** (usually detected automatically) |
   | Root Directory | **`frontend`** (click *Edit* and select the folder) |
   | Build Command / Output Directory | Leave the defaults (`npm run build` / `dist`) |

4. Under **Environment Variables**, add:

   | Name | Value |
   |---|---|
   | `VITE_API_URL` | Your Render API address **without** `/api/v1`, e.g. `https://north-street-api.onrender.com` |

   Vite bakes this value into the JavaScript at build time. If you change it later, you must **redeploy** for it to take effect.
5. Click **Deploy**. When it finishes, Vercel shows your address, e.g. `https://north-street-booking.vercel.app`.

### Connect the two

- If the Vercel address is **exactly** what you entered as `CORS_ORIGINS` on Render, you're done.
- If it's different (for example because the name was taken), go to Render → `north-street-api` → **Environment**, update `CORS_ORIGINS` to the real address (no trailing slash) and save. Render redeploys automatically.

### Check that it works

1. Open your Vercel address. The page loads. With an empty database the service list is empty; that's expected.
2. Open `<vercel address>/admin` **directly** in a new tab. You should see the login page, not a 404; `frontend/vercel.json` makes this work.
3. Log in. The first request can take up to a minute while the Render API wakes up.
4. Add barbers and services on **Team & services**, then make a booking on the customer page.

### If something doesn't work

Open the browser's DevTools (**Cmd + Option + I**) → **Console**:

- **`blocked by CORS policy`**: `CORS_ORIGINS` on Render doesn't match your Vercel address exactly (check `https`, the spelling, and that there's no trailing `/`).
- **Requests go to `localhost:8000`**: `VITE_API_URL` wasn't set when the site was built. Set it in Vercel → Settings → Environment Variables, then **Deployments → ⋯ → Redeploy**.
- **`Failed to fetch` after a long wait**: the API is still waking up, or failed to start. Check the Render logs.

Vercel redeploys the frontend automatically on every push to `main`, and creates a preview URL for every other branch.

## Confirmation emails with Brevo

1. Create a free account at https://www.brevo.com.
2. **Senders, Domains & Dedicated IPs → Senders → Add a sender:** your name or shop name and the email address that should send the confirmations (for example your Gmail). Confirm it with the code Brevo sends to that inbox.
3. **SMTP & API → API Keys → Generate a new API key.** Copy it once; Brevo won't show it again. Don't paste it anywhere else.
4. In Render → `north-street-api` → **Environment**, add:

   | Variable | Value |
   |---|---|
   | `BREVO_API_KEY` | The key from step 3 |
   | `SMTP_FROM_EMAIL` | The sender address from step 2 |

   Save; Render redeploys.
5. Make a booking with your own email address. The Render **Logs** show `Sent booking confirmation #… via brevo`, or the reason if Brevo refused it (for example an invalid key or an unverified sender).

## Free-tier limitations

These are fine for a portfolio demo, but good to know (and to mention when you show it):

- **Cold starts:** the free API sleeps after 15 minutes without traffic. The first request after that takes about a minute; the admin login shows "Logging in…" while it waits.
- **Emails go through Brevo, not SMTP:** free Render services can't connect to SMTP ports (25/465/587), so confirmation emails are sent over HTTPS to Brevo's API (free: 300 emails/day). Without `BREVO_API_KEY`, bookings work normally and only the email is skipped. With a Gmail sender, Brevo shows the sender as "via brevosend.com", because free email domains can't be authenticated; authenticating your own domain in Brevo removes that.
- **Database lifetime:** free Render Postgres databases **expire 30 days after creation**, with a 14-day grace period before deletion. To keep the demo running longer, upgrade the database, or create a new free one and redeploy. Migrations recreate the schema; the demo data has to be added again.
- **Migrations run at startup:** pre-deploy commands are a paid feature, so `alembic upgrade head` runs in the start command. If a migration fails, the new version doesn't start and the previous one keeps serving.

## Updating the live app

Push to `main`. Render redeploys the API automatically (`autoDeploy: true`), including any new migrations.
